# 开发中遇到的问题汇总 — 供导师讨论

> 2026-07-10, 桌面 GUI Agent 项目

---

## 1. 核心瓶颈：2B 模型能力不足

**现象**：无论怎么优化 prompt（few-shot + CoT + 双层架构），Qwen2-VL-2B 都无法可靠完成"打开记事本输入1234"这类简单任务。

**具体表现**：
- 观察屏幕时把 OCR 文本重复一遍，而不是真正理解画面
- 输出高度重复，每步几乎一样 → 触发死循环检测
- 目标不在屏幕上时（如桌面没有记事本图标），不会主动用 Win 键搜索，只会乱点
- 判断层的"分析"经常是 OCR 文字的复读，不是真正的推理

**推论**：2B 模型的视觉理解 + 推理能力是硬天花板，prompt 工程只能改善不能突破。

**可能方向**：
- 用 7B+ 模型（但本地 8GB 显存放不下 Qwen2-VL-7B 的 FP16，约需 14GB）
- API 调用 7B（Ollama/vLLM/云端），本机没有现成端点
- 量化（4-bit 约 4-5GB），但 Qwen2-VL 的量化支持需要验证

---

## 2. OCR 自干扰问题

**现象**：OCR 会识别 agent 自己终端窗口里的文字（`>>>`、日志输出、`PS D:\>`、错误消息），模型看到这些后产生幻觉——它以为终端文字是操作目标。

**已尝试**：
- 关键词黑名单过滤（部分有效）
- 路径/CLI 特征检测过滤（仍有漏网）
- 用户任务文字过滤

**未解决**：终端窗口始终在最前面时，OCR 持续受干扰。判断层说"屏幕上看到 gui_agent、python"（其实都是终端文字），然后输出垃圾策略。

**可能方向**：
- 运行前最小化终端窗口
- 截图时排除终端窗口区域（需要知道终端窗口的位置）
- 用更好的视觉模型区分"终端文字"和"桌面UI文字"

---

## 3. 双层 AI 架构 — 设计正确但未验证

**设计**：
```
判断层(分析策略) → 执行层(精确坐标)
```

**进展**：
- 代码完成，92 个单元测试全部通过
- 同模型复用（加载一次），节省显存
- 降级逻辑（判断层失败→回退单层）

**未验证**：因为没有可用的 7B API，判断层和执行层都用同一个 2B 模型跑，实际效果和单层差不多。双层架构的真正价值（强模型判断 + 轻模型执行）没测到。

---

## 4. 系统崩溃事故

**原因**：`_interactive_loop` 在非 TTY 环境下陷入死循环，任务瞬间失败无延迟重试 → 短时间内产生 4.28GB 日志 → 磁盘 I/O 打满 → Windows 崩溃重启。

**已修复**：
- 日志轮转：RotatingFileHandler（10MB × 3）
- TTY 检测：非终端环境直接拒绝
- 指数退避：连续失败时 2^n 秒等待

**教训**：任何循环都必须有速率限制和 fail-safe。

---

## 5. Agent 运行时会抢占键盘

**现象**：pynput 的 keyboard controller 初始化后，用户无法在终端中输入 `exit` 退出程序。

**可能方向**：
- 加 cancel_event 机制（已实现但只在内部循环中检查，不响应外部 Ctrl+C）
- GUI 模式加停止按钮
- 信号处理的改进

---

## 6. 已做但被删掉的功能

**硬编码"打开软件"快捷操作**：识别到"打开XXX"就 Win→输入→回车，绕过 AI。删掉了，因为它不管屏幕状态（比如任务管理器挡在前面），执行后 AI 接手时已处于错误状态。

---

## 总结

| 问题 | 严重程度 | 状态 |
|------|---------|------|
| 2B 模型能力不足 | 🔴 阻塞 | 需要更强模型 |
| OCR 自干扰 | 🟡 严重 | 部分过滤，未根治 |
| 双层架构未验证 | 🟡 需要资源 | 代码完成，缺 7B API |
| 系统崩溃 | 🟢 已修复 | 日志轮转 + TTY 检测 |
| 键盘抢占 | 🟡 体验差 | 有待改进 |

**一句话**：架构方向（双层 AI + OCR 注入 + prompt 可配置化）是对的，但 2B 模型的"脑子"不够用，需要接上一个真正能推理的模型（7B+ API 或量化本地）。
